# SUPABASE_MAPPING.md

Field-by-field mapping between the frontend domain models (`src/domain/*.ts`) and the live Supabase schema (see [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md)). This is the reference a `SupabaseXRepository` implementation would need when Module 12A begins — it does not implement anything, per this exercise being read-only/documentation-only.

**Legend**

- ✅ **Available** — a column exists with a direct or trivially-typed match.
- ⚠️ **Needs transform** — a column exists but needs translation (enum remap, denormalized-text-to-FK resolution, type coercion) in the repository's mapping layer.
- ❌ **Missing** — no column exists; the repository cannot populate this field from the current schema without either a migration or a hardcoded/derived fallback.

Source of truth for "why" on each ⚠️/❌ is [SUPABASE_AUDIT.md](SUPABASE_AUDIT.md)'s "Raw Observations" section.

## `Transaction` (`src/domain/Transaction.ts`) ← `transactions` table

| Domain field    | Type                                | DB column(s)                                                                   | Status           | Notes                                                                                                                                                                                                                                                             |
| --------------- | ----------------------------------- | ------------------------------------------------------------------------------ | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`            | string                              | `id`                                                                           | ✅               |                                                                                                                                                                                                                                                                   |
| `date`          | string                              | `transaction_date`                                                             | ✅               |                                                                                                                                                                                                                                                                   |
| `merchant`      | `Merchant` (`{id, name}`)           | `merchant` (text)                                                              | ⚠️               | No `merchant_id` FK. Repository must resolve `merchant` text → `merchant_memory` row (or synthesize an id) to build the `Merchant` object. Observed free-text values don't always match `merchant_memory.display_name` exactly (case/formatting).                 |
| `category`      | `Category \| null` (`{id, name}`)   | `category` (text)                                                              | ⚠️               | No `category_id` FK. Observed values `Investment`, `Business`, `Uncategorized` don't exist in `categories` at all — resolution will fail for those until either the category text is fixed at the source or `categories` is extended.                             |
| `client`        | `Client \| null`                    | `client_id` (FK)                                                               | ⚠️               | Column exists and is correctly typed, but is `null` on every sampled row — repository will return `null` for every transaction today.                                                                                                                             |
| `account`       | `TransactionAccount` (non-nullable) | `account_id` (FK)                                                              | ❌ (effectively) | Column exists but is `null` on every sampled row, while the domain type is non-nullable. | `ownerType`     | `'business' \| 'personal'`          | —                                                                              | ❌               | No column. Closest candidate, `type`, is a categorization-status field, not an owner split — confirmed by `monthly_summaries.total_personal`/`total_business` both being 0.                                                                                       |
| `type`          | `'debit' \| 'credit'`               | `transaction_type` (`credit_card` default) or `payment_mode` (`debit` default) | ⚠️               | Neither column is a clean debit/credit boolean; needs a defined derivation rule.                                                                                                                                                                                  |
| `amount`        | number                              | `amount`                                                                       | ✅               |                                                                                                                                                                                                                                                                   |
| `status`        | `TransactionStatus` enum (6 values) | `status` (text)                                                                | ⚠️               | Observed values `auto`, `needs_review` don't match any of the 6 enum values. Needs an explicit value-mapping table (see [MIGRATION_PLAN.md](MIGRATION_PLAN.md) item on status reconciliation).                                                                    |
| `paymentMode`   | `PaymentMode` enum (6 values)       | `payment_mode` (text)                                                          | ⚠️               | Column exists; enum-value alignment unverified against live data beyond the `debit` default.                                                                                                                                                                      |
| `notes`         | string \| null                      | `note`                                                                         | ✅               |                                                                                                                                                                                                                                                                   |
| `duplicateOfId` | string \| null                      | —                                                                              | ❌               | No self-referencing FK. `is_duplicate` (boolean) exists but cannot identify _which_ transaction is duplicated.                                                                                                                                                    |

Also present in the table but with no domain field: `bank_name`, `card_last4`, `account_last4`, `email_source`, `raw_email_subject`, `is_manually_entered`, `merchant_raw`, `confidence`, `category_source`, `processed_at`, `review_status`, `ai_confidence`, `is_recurring`, `tags`, `manually_edited`, `edited_at`, `edited_by`, `client_name`, `user_id`. These are available for future domain-model extension or internal repository use but currently unmapped.

## `BankAccountRecord` / `CreditCardRecord` (`src/domain/Account.ts`, `src/domain/CreditCard.ts`) ← `accounts` table

Both domain records map onto the same physical `accounts` table, discriminated by `account_type` (`Savings`/`Current` → bank account, `Credit Card` → credit card).

| Domain field (shared concept) | BankAccountRecord | CreditCardRecord | DB column | Status | Notes |
|---|---|---|---|---|---|---|
| id | `id` | `id` | `id` | ✅ | |
| name | `bankName`+`accountName` | `bankName`+`cardName` | `institution_name`, `account_name` | ✅ | |
| nickname | `nickname` | `nickname` | `account_nickname` | ✅ | |
| last4 | `last4` | `last4` | `account_number_last4` / `card_last4` / `account_last4` — **three overlapping columns** | ⚠️ | Needs a defined precedence rule for which last4 column wins. |
| balance/outstanding | `currentBalance`, `availableBalance` | `outstanding`, `availableCredit` | `current_balance`, `available_credit` | ⚠️ | Columns exist but are `null` on all 7 live rows. |
| credit limit | n/a | `creditLimit` | `credit_limit` | ⚠️ | Exists, `null` on all rows including the 3 credit-card rows. |
| due date / minimum due | n/a | `dueDate`, `minimumDue` | `payment_due_date`, `minimum_due` | ✅ (structurally) | Present, untested with real values. |
| statement date | n/a | `statementDate` | — | ❌ | No distinct "last statement date" column; `statement_day`/`statement_cycle_day` exist but are cycle-day integers, not a date. |
| network | n/a | `network` (`CardNetwork`) | `card_network` | ⚠️ | Column exists but `null` on all 3 sampled credit-card rows. |
| health | `health` (`BankAccountHealth`) | `health` (`CreditCardHealth`) | — | ❌ | No column; both are computed/derived fields with no stored equivalent — would need a view (`vw_account_health` — not yet built). |
| topMerchant / topCategory | both records | both records | — (derivable) | ⚠️ | Aggregates, same caveat as above — and blocked on the `transactions.merchant`/`.category` FK gap. |
| clientId | both records | both records | — | ❌ | No `client_id` column on `accounts` at all. |
| monthlySpend / monthlyCredits / monthlyDebits | both records | `monthlySpend` | — (derivable) | ⚠️ | Aggregate, no stored column, needs `transactions.account_id` to actually be populated first (currently `null` everywhere). |
| status | `BankAccountRecordStatus` | `CreditCardRecordStatus` | `account_status`, `is_active` | ✅ | Two overlapping status-ish columns (`account_status` text default `Active`, `is_active` boolean default true) — needs a precedence rule. |

Structurally the `accounts` table can support both records once populated, but every derived/aggregate field is blocked on `transactions.account_id` actually being non-null, which it currently is not.

## Dashboard / Analytics (`src/domain/Dashboard.ts`, `src/domain/Analytics.ts`)

Neither maps to a dedicated table — both are aggregation layers over `transactions`/`accounts`/`categories`/`merchant_memory`.

- `vw_dashboard_summary` and `vw_dashboard_accounts` exist and cover a slice of `FinancialSnapshotMetric`/`ConnectedAccount`, but currently return zeros/nulls because the underlying `accounts.current_balance`/`credit_limit` and `transactions.account_id` are unpopulated.
- `AnalyticsSummary`, `AnalyticsTrendPoint`, `AnalyticsCategorySlice`, `AnalyticsRankedRow`, etc. (Module 10, already built against mocks) all require the `vw_monthly_spend`, `vw_cashflow`, `vw_category_spend`, `vw_merchant_spend`, `vw_account_analytics`, `vw_credit_utilization`, `vw_transaction_trends` views CLAUDE.md Part 3 specifies. None of these exist yet (see [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md)'s Views section) — Analytics has no path to live data until they're built, independent of the FK/data-population issues above.
