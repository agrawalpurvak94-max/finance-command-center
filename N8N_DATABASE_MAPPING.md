# N8N_DATABASE_MAPPING.md

Node-by-node comparison of the two live n8n workflow exports against the schema defined in [DATABASE_MIGRATIONS.sql](DATABASE_MIGRATIONS.sql). **No workflow file was edited to produce this document** — this is analysis only, per the Database Foundation phase's Step 6.

**Source files inspected:**

- `n8n workflows/Transactions Workflow C Parser - Experimentation` (84KB, 47 nodes)
- `n8n workflows/Workflow D Bank Statement Processing -Experimentation.json` (72KB, 40 nodes)

---

## Naming reconciliation (documentation only — not a rename)

CLAUDE.md's conceptual model names three workflows: **Workflow A** (Transaction Email Processing), **Workflow B** (Statement Processing), **Workflow C** (Merchant Learning). The actual n8n project files on disk use different names and boundaries:

| CLAUDE.md concept                         | Actual file                                                  | What it really contains                                                                                                |
| ----------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Workflow A (Transaction Email Processing) | `Transactions Workflow C Parser - Experimentation`           | Gmail trigger → parse → categorize → insert into `transactions`                                                        |
| Workflow C (Merchant Learning)            | _(same file)_                                                | Merchant memory lookup/save nodes are embedded in the same workflow as transaction processing, not a separate workflow |
| Workflow B (Statement Processing)         | `Workflow D Bank Statement Processing -Experimentation.json` | PDF statement extraction → insert into `statement_transactions`                                                        |

This document keeps calling them **"Workflow C Parser"** and **"Workflow D"** (their actual file names) to avoid inventing a rename that wasn't requested. If CLAUDE.md's A/B/C labels are meant to be authoritative, reconciling the naming is a documentation decision for whoever owns these workflow files, not something to silently correct here.

## Workflow C Parser — nodes vs. schema

### Structure

Two independent AI-categorization branches feed **two separate insert points into `transactions`**:

1. **Fast path**: `Parse HDFC (regex)` → ... → `Load categories` (queries the real `categories` table) → `Claude Haiku categorize` → `Build row (from AI)` → **`Supabase Insert (transactions)`**
2. **Full path**: Gmail trigger → `Normalize Email` → `Bank Detection` → `Fast Parser` / `Gemini Extraction` → `Lookup Merchant Memory` → `AI Categorize` (Gemini, hardcoded category enum) → `Save Merchant Memory` → `Build Final Transaction Row` → `Prepare Dedupe` → `Dedupe check` → `Confidence & Status` → `Restore Dedupe Context` → **`Save Transactions`**

## Workflow D (Statement Processing) — nodes vs. schema

### Structure

Gmail trigger (banking label) → PDF.co upload/unlock/extract → `Parse AI Response` / `Basic LLM Chain` → per-transaction split → `Normalize Merchant` → `Merchant Lookup RPC` (`/rpc/lookup_merchant`) → `Enrich Transaction` → `AI Categorize1` (Gemini, same 19-value hardcoded enum as Workflow C Parser) → `Save Merchant Memory` (`/rpc/upsert_merchant_memory`) → `Build Final Transaction Row` → **`Create a row`** (native Supabase node, table `statement_transactions`).

A second, apparently older branch (`Build Statement Row` → `Append to Transactions` / `Write ProcessedLog`, both `n8n-nodes-base.googleSheets`) writes to Google Sheets instead of Supabase, using a completely different field-naming convention (`Date`, `Bank`, `Card Last4`, `Merchant_Normalized`, ...). This looks like a retained earlier iteration rather than part of the active Supabase-writing path — **not confirmed either way from the JSON alone** (connection graph shows it's reachable, but whether it's still triggered in production vs. left over from development wasn't verifiable without running the workflow). Flagged for the workflow owner to confirm, not assumed dead.

## What this means for Module 12A / 12B (not acted on here)

Per CLAUDE.md, editing these workflows is Module 12B territory ("connect and verify n8n Workflows A/B/C against the live Supabase schema") — this document only identifies what would need to change, it does not change it. In priority order, the workflow-side fixes that would most unblock the frontend:

1. Add a `statements` insert step to Workflow D and fix `statement_id` to use that row's real UUID — this single change unblocks Module 4 (Statements) and `vw_statement_reconciliation` entirely.
2. Populate `account_id` on both workflows' transaction inserts (resolvable today via `bank_name` + `card_last4`/`account_last4` matched against `accounts` — the data needed to do this already flows through both workflows, it's just never looked up against `accounts`).
3. Fix `Build row (from AI)`'s `raw_email` → `raw_email_subject` field name (or confirm it's silently tolerated, if PostgREST behavior is checked directly).
4. Point both `AI Categorize` nodes' enum at the live `categories` table (mirroring the fast path's `Load categories` pattern) instead of a hardcoded list, so this phase's `DATABASE_SEED.sql` fix doesn't silently drift again the next time someone edits a category.
5. Fix `Create a row`'s `status` field mapping in Workflow D to use the value that was actually computed for it, rather than `category_source`.
